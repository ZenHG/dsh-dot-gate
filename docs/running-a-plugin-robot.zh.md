# 在真机上跑一个插件机器人：真正出问题的地方

这不是设计文档，是一份故障记录。记录的是**本插件**的随行机器人：它监视知识库下的一次写入，
执行项目自己的收尾任务，然后回一行结果。下面每一条都在 Windows + DSH 0.2.2 上实际发生过，
每条都附了产生它的命令或报错原文。

再写一个会跑后台任务的插件之前先读它；配套读 [DECISIONS.md](../DECISIONS.md)——这份记「什么坏了」，
那份记「决定了什么」。

[English](running-a-plugin-robot.md) | 中文

## 一、插件可以「装了、注册了、但什么都不做」

第一版从每个角度看都是装好的，却没有任何效果。「装上了」这个词背后藏着三个不同的问题：

| 层 | 问题 | 怎么答 |
| --- | --- | --- |
| 磁盘 | 包在不在？是 link 还是 copy？ | `Get-Item <profile>\node_modules\<pkg> -Force | Select-Object LinkType, Target` |
| profile | profile 选中它了吗？ | `(Get-Content <profile>\package.json -Raw | ConvertFrom-Json).dsh.profile.bundles` |
| 运行时 | 跑着的宿主真的注册它了吗？ | 插件自己写的痕迹文件，或会话里的证据 |

第三层才是「这个会话能不能用到它」，也正是没人查的那一层。`appliedAt` / `sourceHash` 不算证据：
在 `link:` 安装下它们会更新，而进程里还是旧模块。

## 二、读 `ctx` 上没声明的属性，装载时就会抛

这条代价是四次重启，而且完全看不见——插件在抛之前已经把装载痕迹写下去了。原文：

```
phase=register-error
message: cannot get property "spawn" without inject
stack:   at new apply (.../index.js:163:78)
         at Fiber.execute (.../@deepseek-ai/cordis/lib/index.js:362:24)
```

`ctx` 是 Proxy。读一个没在 `inject` 里声明的 `ctx.<anything>` 会**抛异常**，不是返回 `undefined`。
所以写成 `const spawn = ctx.spawn ?? null` 的插件会死在装载期，死在它前面那行日志之后。

两条值得留下：

- **不要用探测 `ctx` 的方式找可选接口。** 用你自己能控制的模块（spawn 就用 `node:child_process`），
  需要假的执行器时让测试通过 config 注入。
- **记「阶段」，不要只记一行「已加载」。** 注册前写 `enter`，最后一个 `ctx.on(...)` 之后写 `ready`。
  两者之间的距离就把故障定位到具体一步。只包住第一个调用的 try/catch 比没有更糟：它看起来像保护，
  实际不是。

一条本可以抓住它、现在也确实抓住它的回归测试：

```js
const guarded = new Proxy({}, {
  get(_t, prop) {
    if (prop === 'on') return (ev, fn) => handlers.set(ev, fn)
    if (prop === 'logger') return { warn() {} }
    throw new Error('cannot get property "' + String(prop) + '" without inject')
  },
})
assert.doesNotThrow(() => apply(guarded, config))
```

## 三、重启到底改了什么，没改什么

- `dsh plugin --profile <name> add <spec>` 转发给 pnpm，**并且**在我们测的版本上会自动把包追加进
  `dsh.profile.bundles`。早前"它只动依赖"的笔记属于更早的构建。
- `link:` 的包在运行中的宿主里**不会重新求值**。改源码只改磁盘，不改进程。要加载新代码只能重启。
- 当配置是喂给 `apply(ctx, config)` 的时候，配置改动也需要同一次重启，因为那函数只跑一次。

如果一次改动需要重启，就**同时**排一个重启后复查的任务。带看门狗的重启是好的；
排了重启却没人读结果的，会让一个坏掉的构建躺几个小时。

## 四、后台任务必须能说清自己跑没跑

四件事决定了它是「一个偶尔跑跑的脚本」还是「一个可以信的机器人」：

**记全阶段。** `enter`、`ready`、`register-error`，以及每次执行的 `run` 行（带退出码）。
这样「什么都没发生」就从一个静默状态拆成四种可区分的情况。

**给一个状态命令，并且把"插件没装载"单列成一种状态。** 我们的返回值是
`ok | plugin-not-loaded | register-error | not-ready | no-runs-observed | stale-runs`，不是 `ok` 就非零退出。
`plugin-not-loaded` 单独存在是关键：**它是插件唯一没法自己报告的那种失败。**

**报告要短。** 成功时静默的步骤是值得的。我们跑三条命令，第三条只在失败时才出现，因为
每加一个功能就把报告加长一行的东西，加到第五行就没人读了。注意那个标记必须跟着**结果**走，
不能只在配置里——我们第一版在组装结果时把它丢了，而单测是直接拿配置好的字段调汇总函数的，所以全绿。

**给噪音封顶。** 只靠静默期防抖会饿死：一直在改就一直不安静，收尾永远不跑。必须配一个从**第一条**
排队项算起的硬上限。同时要给「每回合最多跑几次」封顶，否则一个失控的循环会无限触发。

## 五、同时只允许一个写者——这条规矩仓库里本来就有

这台机器上同时跑着两个宿主实例，第二次索引构建撞上了第一次：

```
PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问: '<index>.sqlite'
```

收尾任务会删掉并重建那个文件，所以在并发下不安全。我们照抄的正是 `ds-bot/src/host/home-lock.js`
里的规则，这里值得重复，因为**不好想的那一半很容易漏**：

> 活着的持有者需要**同时**满足「pid 还在跑」和「心跳够新」——崩溃的持有者留下的 pid 可能被
> 无关进程复用，不做心跳检查的话，那个无关进程会在它运行的整段时间里一直占着锁。

我们实现成一个带 `{pid, at}` 的锁文件，每次运行刷新，加同样的两条件存活判定。钉住它的测试：

- 活着的持有者（真的 spawn 一个独立进程）会让本次运行**跳过**并说明原因；
- 死掉的持有者会被接管；
- pid 活着但心跳过期，按死锁处理。

## 六、会说谎的健康检查

有两种让重启脚本报「成功」而应用根本不可用的写法：

**接受任何小于 500 的响应。** 宿主监听不止一个端口：一个回应用（未鉴权时 401，或 200），
另一个在 `/` 上回 404。写成「小于 500 就算健康」的探针于是永远命中旁路服务，每次重启都打印错误
的 URL。改成按响应本身排序——401 最优，其次 2xx/3xx，再次 404，只有 404 就判为未提供服务——
就修好了，验证方式是一次干跑终于打出了 UI 的端口。

**拿 UTC 去比本地时间。** 插件的痕迹存的是带 `Z` 的 ISO 时间，进程启动时间是本地时间。
直接比较会在第一次运行就把健康的插件报成死了。这是监控里最糟糕的一种 bug：
**一次假警报通常就够让人把它静音。**

## 七、从外面盯着它，否则你就是那个监控

插件只能在它自己被装载的时候报告。如果它没装载、或者不再运行，唯一的症状就是沉默，
而沉默和「今天没发生什么事」长得一模一样。

办法是一条不依赖插件的检查：一个计划任务，比对几件本应一致的事实——

- 宿主在不在跑、什么时候启动；
- 插件痕迹里有没有比这次启动更新的 `ready`；
- 被监视的目录有改动，而机器人一直没跑。

它写一个告警文件并弹通知，**带冷却**——每十分钟响一次的警报会被静音，那就比没有更糟。

## 八、如果重来一次

- 先写 `doctor` 命令，再写功能。状态清单确定之后只花十分钟，而它能省掉每一次重启。
- 不要写一个失败了还不留痕的插件。一个插件自己拥有的日志文件，是"能诊断"和"只能猜"的分界线。
- 把「装上了」当成一个需要命令来证明的主张，而不是一个可以假设的状态。
